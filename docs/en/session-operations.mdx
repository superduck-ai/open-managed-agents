Once a session exists, use these operations to read, update, archive, or delete it. See [Start a session](/docs/en/sessions) for creating a session and sending it work.

<Note>
  Beta requirements differ by resource. See [Versioning and beta features](/docs/en/api/versioning-beta), and verify that your SDK sends the parameters required by OMA.
</Note>

## Session statuses

Sessions progress through these statuses. See [Start a session](/docs/en/sessions) for the session lifecycle.

| Status         | Description                                                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `idle`         | Agent is waiting for input, including user messages or tool confirmations. Sessions created without `initial_events` start in `idle`.                   |
| `running`      | Agent is actively executing.                                                                                                                            |
| `rescheduling` | Transient error occurred, retrying automatically.                                                                                                       |
| `terminated`   | Session has ended, either because of an unrecoverable error or because it was archived. A session that finishes its work goes `idle`, not `terminated`. |

## Updating the agent configuration

You can update a session's `agent.tools` and `agent.mcp_servers`, including permission policies, mid-session without creating a new agent version. Updates are session-local and do not propagate back to the underlying agent.

Only the agent's `tools` and `mcp_servers` can change after a session is created. To run a session with `model`, `system`, or `skills` values other than the agent's, use [agent configuration overrides](/docs/en/sessions#override-agent-configuration-for-a-session) when you create the session. The agent's model configuration cannot change mid-session. The agent's configured `system` field is fixed for the session's lifetime. On models that support it, you can still append system-level guidance mid-session by sending a [`system.message` event](/docs/en/events-and-streaming#sending-system-messages).

The semantics of a `tools` or `mcp_servers` update are full replacement: the provided array is the new value. To preserve existing entries, `GET` the session, modify the array, and `POST` it back.

The session must be `idle` to update the agent. [Interrupt](/docs/en/events-and-streaming#integrating-events) the session if you need to update the agent while it's running.

<CodeGroup defaultLanguage="CLI">
  ```bash cURL
  curl -sS --fail-with-body "http://localhost:38080/v1/sessions/$SESSION_ID" \
    -H "x-api-key: $OMA_API_KEY" \
    -H "anthropic-version: 2023-06-01" \
    -H "anthropic-beta: managed-agents-2026-04-01" \
    -H "content-type: application/json" \
    -d @- <<EOF
  {
    "agent": {
      "tools": [
        {"type": "agent_toolset_20260401"},
        {"type": "mcp_toolset", "mcp_server_name": "linear"}
      ],
      "mcp_servers": [
        {"type": "url", "name": "linear", "url": "https://mcp.linear.app/sse"}
      ]
    }
  }
  EOF
  ```


## Updating the session budget

A session [created with a budget](/docs/en/sessions#set-a-session-budget) accepts two kinds of budget update: replacing the cap with a new `max_list_cost`, and removing it by setting `budget` to `null`. An accepted update clears the reached marker; inspect the session status and send a new message as needed to continue work. A replacement cap can be higher or lower than the current one, but it must be strictly greater than the session's consumed list cost, and removal is one-way: a non-null `budget` is accepted only on a session that currently has one, so you can't re-add a removed budget or add one to a session created without it. See [Session budgets](/docs/en/budgets#resume-a-session-at-its-budget) for request examples, the error behaviors, and what counts toward list cost.

## Listing sessions

`GET /v1/sessions` returns `data` and `next_page`. Set `limit` for the page size and pass a non-null `next_page` unchanged as the next request's `page`. The API does not return `prev_page`; retain previous results or request cursors in your client to go back. Keep sorting and filters consistent while traversing pages. `order` sorts by creation time and defaults to `desc`.

```bash
first_page=$(curl -sS --fail-with-body --get "$OMA_BASE_URL/v1/sessions" \
  -H "x-api-key: $OMA_API_KEY" \
  --data-urlencode 'limit=20')
printf '%s\n' "$first_page" | jq '.data'
next_page=$(printf '%s\n' "$first_page" | jq -r '.next_page // empty')
if [ -n "$next_page" ]; then
  curl -sS --fail-with-body --get "$OMA_BASE_URL/v1/sessions" \
    -H "x-api-key: $OMA_API_KEY" \
    --data-urlencode 'limit=20' --data-urlencode "page=$next_page"
fi
```

See [Authentication](/docs/en/api/authentication) for `OMA_BASE_URL` and `OMA_API_KEY`, and [Pagination](/docs/en/api/pagination) for resource-specific behavior.

## Archiving a session

Archive a session to prevent new events while preserving its history. An executing task can block archiving; send an [interrupt event](/docs/en/events-and-streaming), wait until the session can be archived, and retry.

  ```bash cURL
  curl -fsSL -X POST "http://localhost:38080/v1/sessions/$SESSION_ID/archive" \
    -H "x-api-key: $OMA_API_KEY" \
    -H "anthropic-version: 2023-06-01" \
    -H "anthropic-beta: managed-agents-2026-04-01"
  ```

## Deleting a session

After deletion, session records and events are no longer accessible and associated resources enter cleanup. An executing task can block deletion; send an [interrupt event](/docs/en/events-and-streaming), wait until the session can be deleted, and retry. Physical cleanup can complete asynchronously.

Memory stores, vaults, skills, environments, and agents are independent resources and are not affected by session deletion. Files you uploaded through the Files API are also unaffected, but files the session itself produced are scoped to it and are permanently deleted along with its filesystem. Download anything you need to keep before deleting the session.

<CodeGroup defaultLanguage="CLI">
  ```bash cURL
  curl -fsSL -X DELETE "http://localhost:38080/v1/sessions/$SESSION_ID" \
    -H "x-api-key: $OMA_API_KEY" \
    -H "anthropic-version: 2023-06-01" \
  ```
