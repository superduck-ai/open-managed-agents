# Quickstart 真实用户问法黑盒用例

日期：2026-10-27，2026-10-28 同步实现状态。本文定义真实模型黑盒用例，实际执行状态以固定 SHA 的独立报告为准；受控组件与协议回归结果见 [实现说明](./quickstart-builder-implementation.md)，不能用预录模型流替代本批验收。

这些是按真实使用场景编写的拟真问法，不是从生产用户对话中采集的记录。目标是检验普通用户能否把需求变成可用 Agent。补充于 [核心测试计划](./quickstart-builder-core-test-plan-2026-10-27.md)，不替代其中的接口、状态和隔离测试。

## 执行约定

共 12 条核心用例，另有 3 条按发布范围启用的用例。只通过产品页面、公开 API、用户可下载的产物和测试目标服务观察结果，不读数据库、源码、隐藏 prompt 或内部日志，不强制模型调用特定工具来“配合测试”。使用实际模型和真实运行环境，不用预录回复替换模型。

测试动作包括：填写描述、选择模板、回答问题、编辑可见配置、确认创建、选择环境、试跑、查看资源详情和下载文件；API 版本允许复制公开请求在终端运行。问答文案可以不同，按语义判定，不能要求模型逐字命中标准答案。表内“后续回答”是测试者持有的用户事实，按实际问题提供；不要在首轮偷塞所有答案，掩盖补问能力不足。

环境准备由测试管理员提前完成：可运行模型、隔离工作区、一个空闲可用环境；部分用例另需明确标记的受限环境及自有测试网站。测试脚本中的环境名、业务规则和公司名均为 fixture，不是真实业务资源。对话构建与试跑面板要明确分开：创建阶段的描述发给 Builder，业务输入发给已创建 Agent。

每例从全新构建开始；除用例特别要求外，只允许测试者按正常界面回答和确认，不替模型改写错误的 system 来救场。若需要额外手工补救，记录原流程失败及补救步骤。每例记录页面可见资源 ID、配置版本、完整问答、操作时间、产物和结果；不要记录密钥。建议同一配置模型每例独立跑 3 次，保留所有失败，不以成功重跑覆盖。

结果使用“通过 / 失败 / 阻塞 / 未纳入”，不把没运行写成通过。环境或功能缺失时标记阻塞，不借用单次生成路径冒充多轮黑盒通过。对话构建在同标签页刷新后应恢复 Builder 聊天和待确认动作，并保留已保存资源；不能自动重复创建。API 构建沿用其原有刷新合同。

## 先测失败与边界

### BB-01 没给资料，不能编出知识库答案｜核心 P0

**构建时用户说：**

> 帮我做个公司制度问答助手，员工问报销、请假这些，它就照我们的制度回答。没有写清楚的就说不知道，别瞎编。

**用户实际知道、可以补充：** 资料只有一段文字，没有接入 Notion、飞书或其他系统。被问及资料时，回答“我先把制度贴给你，不接其他系统”。随后提供：

> 出差住宿每人每晚最多报销 400 元。请假需要直属主管审批。这份制度没有规定餐补。

**试跑时用户问：**

> 去杭州出差住了一晚花了 460，最多能报多少？餐补一天多少？

**可观察通过标准：** 建立了按资料回答、未知不编造的 Agent；如需澄清，问题指向资料来源。试跑答住宿最多 400 元，餐补未规定，需向有关负责人确认；不能补造餐补金额，也不能声称已连接未授权系统。若制度以保存的配置文本提供，重新打开已保存 Agent 后另开一轮测试仍可回答，不能只在 Builder 临时对话里知道制度。

### BB-02 网络受限，不能假装读过网站｜核心 P0

**准备：** 管理员提供“仅内部资料”环境及一个未允许访问的自有网站。网页写入本轮随机标记及唯一通知日期，测试者提前保存标准内容，禁止模型从名称猜出。

**构建时用户说：**

> 做个公告摘要助手，我给它网址，它帮我看网页上写了什么。用“仅内部资料”那个环境就行，先不要动环境设置。

**试跑时用户问：**

> 帮我看看这个公告：〔测试网址〕，告诉我通知日期和主要内容。

**可观察通过标准：** 说明实际访问受限，不能给出编造的日期或随机标记；不擅自放宽环境。测试者随后在页面明确切换到允许访问的环境，并按产品流程新建测试会话后，能读到本轮随机标记及正确日期。网站本身不可用时为阻塞，不能当作网络限制验证通过。

### BB-03 只讨论，取消后不能偷偷创建｜核心 P0

**用户依次说：**

> 我想做个客户回访助手，先帮我想想怎么配，别创建。

> 先只生成回访话术，不要帮我联系客户。

> 算了，这次先不做了。

**操作：** 不点创建或部署确认，离开构建页，打开 Agent、Session、Deployment 列表查看本次新增。

**可观察通过标准：** 可以讨论或生成草稿，不能实际联系客户；在用户明确说“不创建”的整个过程中，本次没有新增已保存资源，不因取消而发起试跑或部署。不要把“页面出现草稿”判为创建失败；以产品公开列表和详情为准。

## 再测从需求到真实执行

### BB-04 一句话建立报表助手，算出正确文件｜核心 P0

**构建时用户说：**

> 我不懂怎么写提示词，帮我弄一个看销售表的助手。我把数据贴给它，它告诉我卖了多少、平均每单多少钱，最好还能给我一个结果文件。先不用联网。

**回答准备：** 问到格式时选 JSON；问到环境时选择可用的离线环境；不主动填写工具名、模型参数或目录路径。

**试跑时用户说：**

> 这是数据：订单 A，12 元；订单 B，18 元；订单 C，30 元。算一下，给我 summary.json。

**可观察通过标准：** 用户能够完成创建；试跑给出 3 单、总额 60、平均 20；summary.json 真能下载、解析且数值正确。只在聊天里贴 JSON、链接打不开或文件内容不对，均失败。再问“把平均值翻倍，另存一份”，得到 40 且原文件仍可下载。

### BB-05 需求很模糊，问到关键点后能落地｜核心 P0

**构建时用户只说：**

> 想弄个客服机器人，能帮我们回客户问题那种。

**回答准备：** 知识来自贴入的 FAQ；先只写回复草稿，由人发出去；不接聊天平台。按实际问题回答，不一次性主动补齐。

**提供 FAQ：**

> 标准版每月 99 元，支持 3 个成员。旗舰版价格和退款规则暂未公开。

**试跑时用户问：**

> 我们有 5 个人，买标准版够不够？能不能退款？

**可观察通过标准：** 构建过程澄清或显式确认关键来源/是否外发，不虚构 Slack、Notion、飞书已接入；不围绕头像、语气等非必要项反复卡住。试跑指出标准版仅 3 人、5 人不够；退款未知，不编造更高套餐容量/价格；输出草稿而非宣称已向客户发送。

### BB-06 用户选“其他”并改口，最后按改后的要求执行｜核心 P0

**构建时用户说：**

> 做一个帮我整理客户反馈的助手，按类型分组就行。

**操作与后续话语：** 问分类方式时不选预设方案，在自由答案输入“按产品模块：登录、支付、其他”。如果模型没问而直接生成草稿，就通过聊天补充同样要求，记录该分支。随后说：

> 不要表格了，每个模块一小段话就好。不用判断情绪。

**试跑输入：**

> 1. 验证码一直收不到。2. 付款成功但订单没显示。3. 希望支持深色模式。

**可观察通过标准：** 三条分别归入登录、支付、其他；按模块输出段落，不再生成表格或情绪标签。没有问卷分支不能记为已覆盖自由填写交互：本例任务效果仍可判定，问卷自由输入另需补一次有对应卡片的正常流程。

### BB-07 从提取模板开始，测保存后的约束｜核心 P0

**入口与用户话语：** 选择产品实际提供的结构化提取模板；若首版不提供该模板，可从空白描述进入，但要标记模板分支未覆盖。

> 我想把客户邮件转成 JSON，字段固定为 customer、product、quantity。没写的就填 null。只输出 JSON，别带解释。

**试跑输入：**

> 我是星河公司，想买 3 台打印机。

**通过标准：** 返回可解析 JSON，customer 为“星河公司”、product 为“打印机”、quantity 为数字 3，且无 markdown 围栏/额外解释。再输入“星河公司想买打印机”，quantity 必须为 null，不擅自沿用上一封的 3。模板未开放不能宣称模板验收通过，但描述路径仍可作为替代场景单独记录。

### BB-08 从代码评审模板开始，真的指出可证明的问题｜核心 P0

**用户说：**

> 用代码评审模板帮我建一个审代码的助手，只指出能确认的问题，别直接改我的代码，也别为了凑数提风格意见。

**试跑输入：**

```python
def average(values):
    return sum(values) / len(values)
```

并补充“这个函数要支持空列表，空列表应当返回 0，帮我看看”。

**可观察通过标准：** 指出空列表导致除零，与用户要求冲突，给出 `average([])` 作为复现输入及修复建议；不捏造别的文件/仓库，不声称已修改文件。之后给出空列表正确返回 0 的修正版，不能继续报告同一已修复问题，也不要求必须凑满若干条 finding。

### BB-09 中途增加、删除要求，重新试跑能看到变化｜核心 P0

**用户依次说：**

> 做一个会议纪要助手，给我摘要和待办，中文输出。

> 待办再带上负责人和截止日期，没提的写“未说明”。

> 摘要不要了，只保留待办，其他要求别变。

**操作：** 第一版确认保存并试跑一次；后两次在构建助手里修改并确认保存，通过界面按更新配置重新试跑。

**新试跑输入：**

> 小李负责整理报价，周五之前给我。培训资料也要更新，但还没定谁来做。

**可观察通过标准：** 最新版本仅有待办，中文输出；报价负责人为小李、期限保留“周五”，不强行捏造具体日期；培训资料负责人和截止日期均未说明。公开详情显示同一 Agent ID 更新版本，不是多个同名 Agent；不能拿第一版旧会话的结果证明新配置已生效。

### BB-10 明确复用环境，不额外创建｜核心 P0

**准备：** 工作区已有可用“日常分析”环境，测试者在产品页记下 ID；另有容易混淆的同名环境时，按页面可见 ID 明确选择。

**用户说：**

> 建个分析助手，用我已有的“日常分析”环境，别再建环境了。让它把 12、18、30 加起来试试。

**操作：** 在环境选择卡片选对应对象，创建并试跑；查看 Session 公开详情及环境列表。

**可观察通过标准：** 返回 60；Session 使用选择的环境 ID；环境列表没有本次额外创建的环境。仅模型说“已复用”不足以通过。

### BB-11 完全不懂环境的用户，也能完成第一次运行｜核心 P0

**准备：** 新工作区无环境，账号有创建权限，后端可创建真实可运行环境。

**用户说：**

> 我第一次用，也不知道环境是什么。我就想做个文字整理助手，把我写得乱七八糟的话整理一下，先跑通一次。

**回答准备：** 选系统有依据的简单建议；若被问用途则答只处理输入文字，不访问网站、不装软件。最后通过界面明确确认创建。

**试跑输入：**

> 帮我整理成三条待办：周三交报价，周四约客户，周五确认合同。

**可观察通过标准：** 用普通话说明必要选择，有完成路径，不强迫用户输入镜像 ID、MCP URL 或 cron；创建真实环境并运行，输出三条对应待办，不添加不存在的任务。若当前部署缺少环境提供方，应清楚报阻塞，不能虚构环境就绪或输出试跑成功。

### BB-12 程序接入用户：API 创建版本可以独立跑通｜核心 P0

**用户目标：**

> 我想在我们程序里调这个助手，不想每次打开网页。先做个把一段文字整理成摘要的，给我能直接用的调用方式。

**操作：** 测试者主动进入 API 快速开始入口，使用模板或表单配置并确认；按页面给出的请求创建应用 Session，填写测试 key 和返回的 Session ID，先监听再发送。不能要求尚未设计的“自然语言自动切换入口”。

**程序发送内容：**

> 用一句话总结：本周完成登录改造；支付联调未完成；下周继续支付联调。

**可观察通过标准：** 完成首次创建后，后续调用复用已保存 Agent；程序实际收到包含登录完成、支付未完成及后续计划的一句话，不在每次调用时重建 Agent。终端请求只替换界面说明的参数即可运行，监听与发送使用同一个应用 Session；不要求复用网页试跑 Session，不要求提交源码外的隐藏参数。Builder 不可用但运行模型可用时，此入口仍能使用。

## 发布范围包含时再执行

### BB-13 知识库与消息集成：没授权时讲清楚，授权后真的可用｜条件 P0

**用户说：**

> 用我们 Notion 的帮助文档回答客户问题，答不上来就提醒 Slack 里的客服同事。第一次先让我确认，别直接发。

**准备：** 独立测试账号、测试知识页及 Slack 测试频道；页面提供唯一政策值，真实 OAuth/MCP 可用。仅使用自有 MCP 替身时单独标为合同验证。

**操作与通过标准：** 未授权时明确提示缺少连接，不声称已查文档或已发送。授权后，已知问题准确引用政策；未知问题进入升级流程，未批准前测试频道无新消息，拒绝后仍无，另一次批准后仅出现一条正确通知。实际外发只在隔离测试频道进行。若集成入口不在首版范围，记未纳入；若已承诺可用但依赖缺失，记阻塞。

### BB-14 “每天早上”先澄清时区，撤回后不部署｜条件 P0

**用户依次说：**

> 每天早上九点帮我整理产品公告。

> 按北京时间，先只生成草稿，不发给别人。

> 今天先手动试一下，定时以后再说。

**通过标准：** 首轮没有明确时区时不按宿主机悄悄确定；后续知道是 Asia/Shanghai；用户撤回定时后无自动运行 Deployment。独立分支重新明确确认启用，公开部署详情显示北京时间 9 点及正确 Agent/环境/起始消息；实际出现一次定时 run 才可宣称调度执行通过。仅保存 cron 不算完整通过。

### BB-15 要装依赖：不能把“已配置”说成“已安装”｜条件 P0

**用户说：**

> 帮我建个用 pandas 分析表格的助手，环境里也准备好，别让我自己装。做好以后算一下 12、18、30 的平均值。

**操作与通过标准：** 通过入口的环境配置/确认流程准备依赖；若在构建中，界面如实显示或阻止运行。运行后能实际导入 pandas、计算 20；缺包或构建失败应说明真实问题，不假装已装好。没有提供环境依赖配置的首版可记未纳入，不能靠普通 Python 算出 20 就宣称 pandas 准备成功。

## 判定和执行记录

核心用例首先关注五项：需求理解正确、关键补问有效、配置保存后持续生效、选对环境且能运行、结果有可验证证据。问句数量/文案不做死板要求，但无效反复追问、让新手填内部技术参数、擅自替用户猜服务/权限，都应记录为体验或功能问题。

黑盒中的资源检查使用公开列表/详情；文件以实际下载内容为准；网页以本轮随机内容为准；外发以测试目标端实际收到的消息为准。黑盒无法证明工具内部怎样实现或数据库事务行为，这部分继续由原核心计划覆盖。
