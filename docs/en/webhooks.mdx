<Note>This guide describes current OMA webhook behavior and differences from Claude. OMA currently implements subscription management and delivery for 35 Session/Vault/Credential/Environment/Memory Store/Agent/Deployment/Deployment Run events. The catalog also accepts three reserved types (`session.budget_reached`, `agent.deleted`, and `deployment.deleted`), for 38 selectable types in total; these reservations currently produce no notifications. See the [current Webhooks API contract](/docs/en/api/resources/webhooks) for implementation limits. Automatic disabling and transactional enqueueing still differ from the target behavior; custom attempt limits can also differ.</Note>

Deployment Run subscriptions support `deployment_run.started`, `deployment_run.succeeded`, and `deployment_run.failed` for scheduled runs only; manual runs emit none. The existing transaction persists the Run and Session-creation result together. After commit, started and the result are enqueued with the same Run ID, so started is not a live in-progress signal. Succeeded means a Session was created, not that its work finished. Failed means a business failure was persisted without a Session; database rollbacks, stale jobs, and duplicate occurrences do not notify. Data contains only the four identifier fields. Follow the Run's session_id for subsequent execution.

Deployment subscriptions support `deployment.created`, `deployment.updated`, `deployment.paused`, `deployment.unpaused`, and `deployment.archived`. The shared Store notifies only after the resource and River schedule transaction commits. Updated requires an actual property change; pause/unpause require a status transition. Archive covers direct operations, Agent cascades, and the scheduled archive branch. No-op updates and repeated operations do not notify; last_run_at changes from ordinary runs do not emit updated. Repeating a manual pause may still change the pause reason as before, without another paused event. Data contains only event type, Deployment ID, and tenant identifiers. `deployment.deleted` is accepted as a reserved subscription. There is no Deployment delete API or producer, so it currently generates no notification; direct or cascading archival does not emit deleted. Resource commits and enqueueing remain non-atomic.

Environment subscriptions support `environment.created`, `environment.updated`, `environment.archived`, and `environment.deleted`. Creation refers to the environment record, not sandbox readiness. Updates notify only when persisted attributes change; no-op updates and repeated archives preserve timestamps and emit nothing. Deletion notifies after the existing transaction succeeds, including deletion of an archived environment; active work still blocks deletion. Work/heartbeat/sandbox state changes do not emit these resource events. Production SDK fixture bypasses have been removed; all identities follow the same persistence and notification rules. Payloads contain identifiers only. Delivery uses workspace subscriptions only.

Sessions created by manual or scheduled Deployment runs emit `session.status_idled` after the transaction commits. Creating the primary thread does not emit child-thread events, and defining an initial outcome does not emit `session.outcome_evaluation_ended`; that event follows an actual evaluation-end event. Failed runs and duplicate scheduled occurrences do not create new notifications. Two independent manual runs notify separately.

Sessions are long-running interactions. While most real-time interactions happen through the [SSE event stream](/docs/en/events-and-streaming), webhooks notify you of major state changes.

Webhook events return the event `type` and `id`, not the full object. When you receive a webhook event, you need to fetch the object directly with a `GET` call. This avoids delivering stale data on retries and keeps every delivery small.

## Register an endpoint

Visit **Manage > Webhooks** in the OMA Console.

Choose a workspace and select **Add webhook endpoint**. Name and description are optional. Events start unselected; select at least one. The editor supports per-group selection, select all, protocol-name copy, and URL validation. Details support URL/metadata/event edits, enable/disable, deletion, and secret rotation. Save the one-time secret before closing its dialog.

The delivery worker starts by default and uses database subscriptions only. Set `webhook.worker_enabled: false` to disable it on this instance.

OMA currently delivers up to 10 jobs concurrently per worker instance and waits for the whole batch before polling again. Instances have independent limits; delivery order is not guaranteed. A queued database-subscription job whose endpoint has been deleted, disabled, or cannot be resolved in its workspace is skipped and completed without sending or updating subscription statistics. Endpoint settings are read at claim time; later changes cannot recall an in-flight request.

Events without an enabled matching subscription in their workspace do not create delivery jobs, including after deletion of the last subscription. Historical jobs without a subscription UUID are claimed normally and completed without HTTP delivery, attempt increments, or subscription statistics changes. Pending/retry jobs and expired running jobs can be collected; unexpired running jobs are not stolen, terminal jobs stay terminal. Payloads are not rewritten or rebound to subscriptions. When the worker is disabled, those jobs wait for a future worker. The receiver SDK variable `ANTHROPIC_WEBHOOK_SIGNING_KEY` remains supported; it is not a server delivery setting.

Each claim has a fresh token. Job results and endpoint failure counters commit together only while that claim is current and unexpired. With HTTP timeout T (10 seconds by default), the batch deadline is T+15 seconds and the lease is max(60 seconds, T+30 seconds). Cancellation or a failed result write leaves unfinished jobs recoverable after lease expiry. HTTP delivery can still repeat: deduplicate by event ID. Resource writes and notification enqueueing remain separate commits.

To upgrade from a version with global webhook configuration, stop all old event producers and workers, remove `webhook.endpoint_url`, `webhook.signing_key`, and `webhook.event_types` from YAML, then start the new version. Those fields are rejected even when empty. Create explicit workspace subscriptions in advance if you relied on the global target. Removing global delivery requires no new database migration; existing subscriptions and their signing secrets remain valid. Upgrades from older schema versions must still apply their existing migrations. Retries now default to three total attempts with randomized exponential delays between 5 and 120 seconds. Ordinary failures disable a subscription after a sustained failure window (24 hours by default); redirects and address rejection disable it immediately and terminate the current job. The delivery behavior below describes OMA; remaining Claude differences are listed separately.


A webhook endpoint consists of:

* **URL:** Must be HTTPS on port 443 with a publicly resolvable hostname.
* **Event types:** The list of `data.type` values this endpoint receives. An endpoint only receives events it's subscribed to.
* **Signing secret:** A 32-byte `whsec_`-prefixed secret generated at creation. It's shown only once, so store it securely to verify webhook deliveries.

## Verify the signature

Every delivery carries the `webhook-id`, `webhook-timestamp`, and `webhook-signature` headers. Use the SDK's `unwrap()` helper to verify the signature and parse the event in one step. It throws if the signature is invalid or the payload is more than 5 minutes old.

Set `ANTHROPIC_WEBHOOK_SIGNING_KEY` to the `whsec_`-prefixed secret shown at endpoint creation.

## Handle an event

Parse the body, switch on `data.type`, and fetch the resource by ID. Return any `2xx` to acknowledge. Any other response counts against the endpoint: a `3xx` disables it immediately (redirects are never followed), while other failures are retried; see [Delivery behavior](/docs/en/webhooks#delivery-behavior) for the retry and auto-disable rules.

Every event payload has the same structure, including the event type, identifier, and the timestamp of when the event occurred.

{
  "type": "event",
  "id": "whe_9d5c1f7e...",
  "created_at": "2026-03-18T14:05:22Z",

    "type": "session.status_idled",
    "id": "sesn_01XYZ...",
    "organization_id": "8a3d2f1e-...",
    "workspace_id": "c7b0e4d9-..."
  }

The top-level `event.id` is unique per event, not per delivery. If you receive the same `event.id` twice, it's a retry and you can discard it.

## Delivery behavior

* **Duplicates:** An endpoint can receive the same event more than once, and every attempt delivers the same top-level `event.id` (the same value as the `webhook-id` header). Deduplicate on it.

* **Subscription scope:** An event is delivered only to endpoints subscribed to its type at the moment it's emitted. An event emitted while no endpoint is subscribed to its type is never delivered, and subscribing later doesn't backfill it, so subscribe to an event type before you need it.

* **Ordering is not guaranteed.** Events aren't delivered in the order they occurred: `session.status_idled` might arrive before `session.outcome_evaluation_ended` even if the outcome was produced first, and a `.deleted` event can arrive before the `.archived` event for the same resource. Drive your state from the resource you fetch, not from the order events arrive in.

* **Retries:** OMA defaults to three total attempts, including the first, configurable with `webhook.max_attempts`. After recorded failure n, the retry upper bound is `min(120 seconds, 5 seconds × 2ⁿ)`. The delay is sampled uniformly from `[5 seconds, upper bound)`: the default two retries wait 5–10 and 5–20 seconds respectively. This is OMA's choice of jitter algorithm, not a claim about Claude's unpublished implementation. `run_after` controls eligibility; polling, batch duration and backlog can delay actual delivery further. Workers do not sleep inside a delivery to wait for retries.

* **Terminal jobs and upgrades:** Exhausted attempts and permanent rejection leave the current job `failed`; re-enabling the subscription does not revive it. Other queued jobs retain the existing target check at claim time. Historical payloads, timestamps, counters and scheduled times are not rewritten. At its next claim, a historical job already at the effective attempt limit is terminated without sending, incrementing counters or replacing its last error. Other old jobs use the new retry delay after their next failure. Explicit attempt limits remain honored. HTTP success followed by failed result persistence can still cause redelivery beyond the recorded attempt limit.

* **Timestamps:** The `webhook-timestamp` header is stamped when a delivery attempt is signed and is regenerated on every retry, so retries aren't rejected by the SDK's freshness check. It's the clock for the delivery attempt, not for the event: use the event payload's `created_at` for when the event occurred.

* **Auto-disable:** A `3xx` response immediately disables the subscription with the reason `auto-disabled: endpoint URL returned a redirect (3xx)`; redirects are never followed. DNS results with no permitted public address immediately disable it with `auto-disabled: endpoint URL resolved to an invalid address`. Ordinary failures disable it with `auto-disabled after sustained delivery failures` when a new failure is recorded at least `webhook.failure_disable_after` after the first failure without an intervening success. This positive duration defaults to `24h`; it is an OMA choice, not a published Claude threshold. A successful delivery resets the window and count. The failure that triggers disabling also terminates its job without scheduling another retry. Concurrent results update statistics in database transaction order. Temporary DNS lookup and connection failures use ordinary retries.

* **Failure-window persistence:** The first recorded failure starts a database-clock window, shared by all workers. Checks happen only when another failure is recorded; an idle endpoint is not disabled by a timer or actively probed. After a long idle period, a success clears the window and a failure may disable it. Existing enabled subscriptions start their window on their first failure after the upgrade; old timestamps are not inferred. Previously disabled subscriptions stay disabled. A changed threshold applies at the next failure. In-flight requests may finish after disabling; accepted results are serialized by the database. Stop old workers before migration and restart to avoid mixing count-based and time-based policies.

* **Connection policy:** Webhooks use a dedicated direct HTTP transport, ignoring `HTTP_PROXY` and `HTTPS_PROXY`. Production URLs require HTTPS on port 443. Every new connection resolves the hostname, filters non-public addresses, and connects directly to a validated numeric IP while retaining the original Host and TLS certificate verification. Mixed DNS results use only public candidates. `allow_insecure` permits local HTTP/private addresses and other ports for testing; it does not enable environment proxies or redirects. Confirm direct egress before upgrading proxy-dependent deployments.

* **Subscription edits:** Omitted fields remain unchanged. Editing URL, name, description or events does not reset worker counters or re-enable an automatically disabled subscription. Explicit enabling clears the reason, failure window and count. Secret rotation and ordinary edits do not clear the window; disabling preserves it. A late success cannot re-enable a disabled endpoint. Explicit disabling preserves an existing reason or uses `manual`.

* **Event time:** Persisted Session events retain their original timestamp; resource changes use the returned creation/update/archive timestamp. Deletes and identifier-only cascades capture time immediately after a successful transaction, and OAuth refresh failures capture the final failure decision. These fallback times represent the application's observation of success, not an exact database commit timestamp. Scheduled Run started uses the Run creation time; its result uses the successful transaction return time. Times are UTC RFC3339 with available fractional precision. Existing queued payloads are not rewritten.

Re-enable a subscription after resolving the failure. Events emitted while disabled are not backfilled. Resource commits and notification enqueueing remain separate, so this is not a durable change log.

### Remaining differences from Claude

The default attempt count and retry bounds follow Claude, but Claude does not publish the exact jitter algorithm. Explicit custom attempt limits are an OMA extension. Claude describes disabling after a sustained failure period without publishing the duration; OMA uses a configurable 24-hour default and the documented sustained-failure reason. Business writes and enqueueing are not atomic, and HTTP success followed by a failed result write may cause redelivery. See the [official webhook guide](https://platform.claude.com/docs/en/managed-agents/webhooks).
