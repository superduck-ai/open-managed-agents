When subagents are enabled, a parent agent can delegate work to them. A subagent runs in a separate thread within the same session and returns its result to the parent thread. You can inspect threads and their events in the session.

## Configure in the console

1. Create the reusable subagents in the workspace and configure their models, prompts, and skills.
2. Create or edit the parent agent and enable **Subagents** in the multiagent settings.
3. Choose whether to allow agents to be defined at runtime; add predefined workspace agents when you need a fixed roster.
4. Save the parent agent, [start a session](/docs/en/sessions), and inspect its child threads.

If inline agents are disabled, add at least one predefined agent. A roster can contain up to 20 distinct agents. Referenced agents cannot themselves have multiagent delegation configured.

## Configure with the API

Set `multiagent` when creating or updating the parent agent. Replace `agent_example` with an agent ID from the same workspace:

```json
{
  "multiagent": {
    "type": "multiagent_20261001",
    "subagents": {
      "type": "enabled",
      "inline_agents": { "type": "disabled" },
      "predefined_agents": [{ "type": "agent", "id": "agent_example" }]
    },
    "workflows": { "type": "disabled" },
    "advisor": { "type": "disabled" }
  }
}
```

`inline_agents` controls whether agents may be defined at runtime. A `predefined_agents` entry can specify a `version`; if omitted, saving the parent pins the referenced agent's latest version at that time. Updating the subagent later does not change that reference: update the parent's roster to use a newer version.

When a session is created, OMA expands pinned versions into its configuration snapshot. Later changes to the parent do not change an existing session's snapshot. Existing `coordinator` configurations remain supported.

<Note>
The `workflows` and `advisor` fields are accepted for configuration compatibility. OMA does not currently execute workflow runs or advisor consultations. The example explicitly disables both.
</Note>

## Inspect threads and handle tool requests

After delegation, a subagent produces its own messages and tool events in its thread. Inspect threads in the session or read them through the [event stream](/docs/en/events-and-streaming). When a tool needs confirmation, use the thread and tool-call details in the request to respond to the right call.

Subagent tool permissions use the session's permission policy. MCP connectivity and sandbox access also depend on the runtime path and environment configuration. Configure the tools and network access the session needs before testing delegated work.
